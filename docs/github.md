# GitHub: الإعداد والتشغيل بالتفصيل

كل ما يخص طبقة استضافة الصور. اقرأه مرة، وبعدها ما راح تحتاجه إلا عند عطل.

---

## 1. ليش GitHub أصلاً

بفر ما يستقبل ملف صورة. يستقبل **رابطاً**، ثم يذهب هو بنفسه ويجلب الصورة
من ذلك الرابط. فالرابط لازم يحقق شرطين:

1. يرجّع بايتات الصورة مباشرة، لا صفحة HTML فيها صورة
2. يرجّع ترويسة `Content-Type` تبدأ بـ `image/`

فحصت `raw.githubusercontent.com` فعلياً وهذا ما يرجّعه:

```
HTTP/2 200
content-type: image/png          ← لملف .png
content-type: image/jpeg         ← لملف .jpg
access-control-allow-origin: *
cache-control: max-age=300
```

الشرطان متحققان. هذا سبب اختياره، لا لأنه "مريح".

**ليش لا جوجل درايف:** روابط المشاركة ترجّع صفحة عارض HTML لا بايتات
صورة. حيلة `uc?export=view` غير موثوقة وجوجل يكسرها دورياً.

**ليش لا رفع الصورة عبر النموذج:** حمولة شريحتين ٤٣٤ كيلوبايت base64.
تمريرها عبر نموذج لغوي هدر بلا فائدة، ويكبر خطياً مع عدد البوستات.

---

## 2. الريبو لازم يكون Public

`raw.githubusercontent.com` **لا يخدم الريبو الخاص بلا توكن**. وبفر ما
عنده توكنك، فراح يفشل في الجلب وتظهر المسودة بصورة مكسورة.

معنى ذلك عملياً: أي شي تحطه في هذا الريبو مرئي للعالم.

**ما يدخل الريبو:** القوالب، التوكنز، الخط، الشعار، نصوص البوستات،
الصور المصدّرة. كلها مواد تسويقية ستُنشر علناً بعد أيام على أي حال.

**ما لا يدخل:** توكنات، قوائم إيميلات التجار، بيانات متاجر، أي ملف
تحليلات، أي شي يخص عميلاً بالاسم. `.gitignore` يستبعد `out/` لكنه لا
يحميك من إضافة ملف بيدك.

قاعدة عملية: قبل أي `git add .`، شغّل `git status` واقرأ القائمة.

## 3. عندك ريبو يشتغل أصلاً

قبل ما تنشئ أي شي جديد: منشورات زيادة يوم ٢٠٢٦-٠٧-٢٦ استخدمت هذا
المسار وخرجت بنجاح على القنوات الثلاث:

```
https://raw.githubusercontent.com/ziadahapp-a11y/apps-images/main/aakam/social/ziadah/FEAT-0003/01.png
```

فحصته: حي، `image/png`، ٧٩٨ كيلوبايت، ٢١٦٠×٢٧٠٠.

يعني الطريقة **مجرّبة على حسابك أنت** لا مقترحة نظرياً. الأنظف أن تدفع
أصول هذا النظام إلى نفس الريبو تحت مسار خاص، بدل ريبو ثانٍ تديره:

```bash
git remote add origin https://github.com/ziadahapp-a11y/apps-images.git
```

مع تعديل مسار الإخراج في `publish.py` ليكتب تحت
`aakam/social/ziadah/<التاريخ>/`. الفقرات التالية تبقى مرجعاً إن أردت
ريبو مستقلاً.

## 3ب. إنشاء ريبو جديد

### الطريقة الأسرع: gh CLI

```bash
# تثبيت (ماك)
brew install gh

# تسجيل دخول، يفتح المتصفح ويضبط المصادقة تلقائياً
gh auth login
```

اختر `GitHub.com` ثم `HTTPS` ثم `Login with a web browser`. هذا يضبط
credential helper، فما راح تُسأل عن كلمة مرور بعدها أبداً.

ثم من داخل مجلد المشروع:

```bash
cd ziadah-social
git init
git add .
git commit -m "init: نظام بوستات زيادة"
git branch -M main

gh repo create ziadah-social --public --source=. --remote=origin --push
```

هذا الأمر ينشئ الريبو ويربطه ويدفع، كل شي في سطر واحد.

### الطريقة اليدوية

1. افتح `github.com/new`
2. الاسم: `ziadah-social`
3. **اختر Public** لا Private
4. لا تضف README ولا .gitignore ولا رخصة، فهي موجودة عندك ووجودها في
   الطرفين يسبب تعارضاً عند أول دفع
5. اضغط Create repository

ثم:

```bash
cd ziadah-social
git init
git add .
git commit -m "init: نظام بوستات زيادة"
git branch -M main
git remote add origin https://github.com/<اسمك>/ziadah-social.git
git push -u origin main
```

## 4. المصادقة

GitHub ألغى كلمة المرور في git منذ ٢٠٢١. عندك ثلاثة خيارات:

| الطريقة | الإعداد | ملاحظة |
|---|---|---|
| **gh CLI** | `gh auth login` | الأسهل، ويجدد التوكن تلقائياً |
| **PAT عبر HTTPS** | توكن بدل كلمة المرور | يحتاج تجديداً يدوياً عند الانتهاء |
| **مفتاح SSH** | `ssh-keygen` ثم إضافة العام في GitHub | لا ينتهي، لكن إعداده أطول |

إذا اخترت PAT: من `github.com/settings/tokens`، أنشئ توكناً بصلاحية
`repo` (أو fine-grained بصلاحية `Contents: Read and write` على هذا
الريبو فقط، وهذا أضيق وأأمن). عند أول `git push` يسألك عن اسم المستخدم
وكلمة المرور: ضع التوكن مكان كلمة المرور لا كلمة مرور حسابك.

لتفادي إعادة اللصق كل مرة:

```bash
git config --global credential.helper store      # لينكس
git config --global credential.helper osxkeychain # ماك
```

## 5. تشريح رابط raw

```
https://raw.githubusercontent.com/ziadahapp/ziadah-social/a3f9c1.../assets/2026-08-02/unit-b-moments-01.jpg
└──────────── المضيف ────────────┘└─ المالك ─┘└── الريبو ──┘└─ المرجع ─┘└──────────── المسار ────────────┘
```

**المرجع** هو الجزء الحساس. يقبل ثلاث صيغ، وكلها ترجّع `200`:

| الصيغة | مثال | المحتوى |
|---|---|---|
| اسم الفرع | `main` | يتغيّر مع كل دفع |
| صريحة | `refs/heads/main` | نفس السابق |
| **commit SHA** | `a3f9c1d...` | **ثابت للأبد** |

## 6. ليش السكربت يثبّت على SHA

هذا أهم قرار في هذا الملف، وسببه عطل صامت.

**السيناريو:** ترندر بوست الأسبوع، تدفعه، تنشئ المسودة في بفر برابط على
`main`. بعد يومين تلاحظ خطأً إملائياً في الشريحة. تصلحه، تعيد الرندر،
تكتب فوق **نفس اسم الملف**، تدفع.

الآن رابط `main` صار يشير إلى الصورة الجديدة. المسودة القائمة في بفر لم
تتغيّر ظاهرياً، لكن الصورة التي ستُنشر تغيّرت تحتها بلا أي إشعار. وقد
يكون تغييرك في اتجاه لم تراجعه للنشر.

**والعكس أسوأ:** الكاش `max-age=300`. لو دفعت تصحيحاً ونشرت بفر خلال
الخمس دقائق، يجلب بفر النسخة **القديمة** المخزّنة. تشوف الملف صحيحاً في
GitHub وتشوف صورة خاطئة منشورة، وتقضي وقتاً تبحث عن سبب غير موجود.

الرابط المثبّت على SHA يلغي الاحتمالين: كل commit له عنوان مستقل، وما
نُشر يبقى كما نُشر. السكربت يقرأ الـ SHA بعد الدفع مباشرة:

```python
sha = sh("git", "rev-parse", "HEAD").stdout.strip()
```

ويكتبه في `manifest.json` تحت `commit`، فتقدر ترجع لأي بوست منشور
وتعرف بالضبط أي نسخة من أي ملف كانت فيه.

## 7. ما يفعله publish.py بـ git

```
repo_info()   git remote get-url origin        → المالك والريبو
              git rev-parse --abbrev-ref HEAD  → الفرع

push()        git add assets/<date>/*.jpg
              git status --porcelain           → هل فيه تغيير أصلاً
              git commit -m "assets: <date>"   → يتخطاه لو ما فيه تغيير
              git push
              git rev-parse HEAD               → الـ SHA

verify()      يجلب كل رابط ويتأكد أن Content-Type يبدأ بـ image/
              ثماني محاولات بتأخير متزايد
```

**ليش الإعادة في التحقق:** بعد الدفع مباشرة قد يرجّع raw رمز `404`
لثوانٍ حتى ينتشر المحتوى على الكاش. محاولة واحدة تفشل بلا سبب حقيقي،
فالسكربت يحاول ثماني مرات بتأخير متزايد قبل أن يستسلم.

لا يوجد ملف إعداد فيه اسم الريبو. كل شي مقروء من git نفسه، فلو غيّرت
اسم الريبو أو نقلته لحساب آخر أو بدّلت الفرع، السكربت يتبع بلا تعديل.

## 8. جدول الأعطال

| العطل | السبب | الحل |
|---|---|---|
| `لا يوجد remote اسمه origin` | الريبو غير مربوط | `git remote add origin <الرابط>` |
| `فشل الـ push` + `Authentication failed` | مصادقة ناقصة | `gh auth login` أو استخدم PAT مكان كلمة المرور |
| `فشل الـ push` + `no upstream branch` | أول دفع للفرع | `git push -u origin main` |
| التحقق يفشل بعد ٨ محاولات، والرابط `404` | الريبو **private** | حوّله Public من Settings ثم Danger Zone |
| التحقق يفشل والرابط `404` والريبو public | دفعت على فرع مختلف | `git branch --show-current` وقارنه بالفرع في الرابط |
| `نوع المحتوى text/html` | الرابط يشير لصفحة `github.com` لا `raw` | تحقق أن `RAW` في السكربت لم يُعدَّل |
| `الـ remote ليس على GitHub` | remote على GitLab أو غيره | هذا السكربت مبني على raw من GitHub تحديداً |

## 9. حجم الريبو مع الوقت

بالأرقام المقيسة: الشريحة الواحدة بين ١٤٣ و١٨١ كيلوبايت.

| | |
|---|---|
| الأسبوع (٣ وحدات، ٤ صور تقريباً) | ٦٠٠ كيلوبايت |
| السنة | حوالي ٣١ ميجابايت |
| توصية GitHub للريبو | أقل من ١ جيجابايت |

يعني عندك عشرات السنين من الهامش. **لا تحتاج Git LFS.**

تنبيه واحد: الصور ملفات ثنائية لا تنضغط تفاضلياً بين الإصدارات. لو
أعدت رندر نفس البوست عشر مرات، العشر نسخ كلها تبقى في التاريخ. عند
التجربة والخطأ، ارندر محلياً بـ `render_slides.py` ولا تدفع إلا الشكل
النهائي.

## 10. فحص يدوي سريع

بعد أي دفع، تأكد بنفسك أن الرابط سليم:

```bash
curl -sSI "<الرابط من manifest.json>" | grep -i content-type
```

المخرج المطلوب:

```
content-type: image/jpeg
```

لو طلع `text/html` أو رمز `404`، لا تنشئ المسودة. أصلح أولاً.
